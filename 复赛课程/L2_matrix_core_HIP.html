手写矩阵核 GEMM:打开 libgemm.so 的源码
gemm_lib_mmac.hip · gfx936 的 v_mmac 指令 · 弃 rocBLAS 省 121MiB

L1 里 CppRunner 的每个矩阵乘都 ctypes 调 libgemm.so 的 gemm_linear_fp16。这一课把这个 .so 的源码 gemm_lib_mmac.hip 打开,逐段读懂:海光 gfx936 的矩阵核指令 v_mmac(不是 AMD 的 v_mfma)怎么用、它要的 fragment 寄存器布局怎么逆向出来、整段 GEMM 怎么写、怎么 hipcc 编译、怎么不调 rocBLAS 省 121MiB 显存。全程白底深字、可打印。

怎么读:这一课比 L1 底层。第 3 章(fragment 布局)是难点也是精华——它是"手写矩阵核"和"调库"的分水岭。看不懂可先记结论(那张 lane→元素 映射图),回头再推。代码框对应 最优项目代码/02_matrix_core_HIP/。

读导读:这一课在干一件"反常识"的事↑

常识是:矩阵乘交给 rocBLAS(厂商库)就好,别自己写。L1 的 gemm_lib.hip(rocBLAS 版)就是这么做的。但本项目发现:rocBLAS 一启动就要加载它的 Tensile kernel 库,白白吃掉约 121MiB 显存——对追求 U(显存)分的我们,这是块大肥肉。于是我们绕开 rocBLAS,直接用 gfx936 的矩阵核指令手写 GEMM,既拿到接近库的速度,又省下这 121MiB。这就是 gemm_lib_mmac.hip 的存在意义。

一句话抓住这一课

矩阵核(对标 NVIDIA Tensor Core)是 GPU 里"一条指令算一个小矩阵块"的硬件单元。海光 gfx936 的这条指令叫 v_mmac。难点不在"调用指令",而在它要求 16×16 的矩阵数据按一种古怪的方式分散在 64 个线程的寄存器里(fragment 布局),这个布局官方没文档,得自己逆向。逆向对了,手写 GEMM 就能 bit-exact 替掉 rocBLAS。

1为什么要手写矩阵核(而不是调 rocBLAS)↑

先看 L1 里 rocBLAS 版 gemm_lib.hip 的 gemm_init 干了啥:它调 rocblas_initialize() 把 Tensile(rocBLAS 的算法库)一次性加载好,这能消掉首样本几秒的懒加载——速度上是对的,但代价是常驻约 121MiB 显存。

三笔账(为什么这笔交易划算)
  • 显存(U):学生单样本峰值才几百 MiB,121MiB 占比可观。省掉它 U 直接 +0.32 分。
  • 速度(V):手写矩阵核 GEMM 在我们这些形状上能到 rocBLAS 的 ~1.9–2.3×(实测 64×64 tile),不慢,甚至更快;再按形状选 tile 还能 +0.07。
  • 精度(W):fp16 输入 + fp32 累加,和 rocBLAS 数学等价,实测 bit-exact,W 不变。

所以结论是:在"显存就是分"的赛制下,把 rocBLAS 换成自己的矩阵核库是净赚。前提是你能写出一个又对又快的矩阵核 GEMM——这就要先搞懂 v_mmac。

2v_mmac 指令是什么↑

GPU 里普通的乘加是"一个线程算一个标量乘加"。矩阵核指令则是一整个 wavefront(海光 64 个线程)协作,一条指令算一块 16×16×16 的矩阵乘加,等于几千次标量乘加,快一个量级。NVIDIA 叫它 Tensor Core(指令 mma),AMD 叫 MFMA(指令 v_mfma)。

★本项目的关键发现:gfx936 用 v_mmac,不是 v_mfma

海光虽是 AMD GCN/CDNA 血统,但 gfx936 的矩阵核指令是 v_mmac,照搬 AMD 的 v_mfma 代码会编译失败或算错。怎么确认的?用 isa_probe.sh 逐条试哪些指令能编译通过(见 3.3)。HIP 里用 builtin 包装:

v_mmac 的 builtin 形态
// 一条指令:c += a × b,16×16×16,fp16 输入 / fp32 累加
// a,b 是 4 个 fp16(half4),c 是 4 个 fp32(f32x4)——每个线程各持有一小片
c = __builtin_amdgcn_mmac_f32_16x16x16f16(a, b, c);

名字拆开看:mmac=矩阵乘加,f32=累加成 fp32,16x16x16=算 C[16×16] += A[16×16]·B[16×16],f16=输入是 fp16。一个 wave64 算一个 16×16 输出块;K 维每次吃 16,K 大就循环累加 K/16 次。

3fragment 布局:这一课的核心难点↑

3.1 什么是 fragment

问题来了:a、b 每个线程只给 4 个 fp16,一个 wave 有 64 线程 = 64×4 = 256 个 fp16,正好装下一个 16×16 矩阵(256 个数)。但哪个线程的哪个槽,对应矩阵里的哪一行哪一列?这套"线程↔矩阵元素"的对应关系,就叫 fragment 布局。它由硬件规定,而 gfx936 的 v_mmac 布局官方没文档——填错一个,结果全错。

3.2 lane→元素 映射(实测逆向出的结论)

这是本项目逆向出的 bit-exact 布局,记住这张图(gemm_lib_mmac.hip 文件头注释就是它):

每个线程在 wave 里的编号叫 lane(0..63)。把 lane 拆成两个坐标: r = lane % 16 (0..15) ← 它负责矩阵的第 r 行 g = lane / 16 (0..3) ← 它负责第 g 组、每组 4 个 K A 的片段(a_frag,4 个 fp16): a_frag[i] = A[ 行=r ][ 列k=g*4+i ] i=0..3 B 的片段(b_frag,4 个 fp16): b_frag[i] = W[ 行=r ][ 列k=g*4+i ] (W 行主序 [N,K]) C 的累加器(acc,4 个 fp32): acc[i] = C[ 行=r ][ 列n=g + i*4 ] i=0..3 直觉:64 lane × 4 槽 = 256 = 16×16。r 选行,g 选"这条 lane 管哪 4 个 K(或哪 4 个 N)"。 关键陷阱:输入按 (g*4+i) 连续取 K,输出却按 (g+i*4) 跳着写 N —— 输入输出布局不对称!
为什么这张图值钱

有了它,写 kernel 时每个线程就知道:该从 HBM/LDS 的哪个地址读自己的 4 个 a、4 个 b,算完该把 4 个结果写回哪 4 个输出位置。这就是"手写矩阵核"全部的难点所在。布局错 → 结果错;布局对 → 和 rocBLAS 一字不差。

3.3 这套布局是怎么逆向出来的(方法论)

没有文档,就用"探针 + 独热法"自己测。这套探路代码在 02_matrix_core_HIP/mmac_*.hip,讲的是遇到无文档硬件时怎么自救:

步骤文件干啥
① 确认指令存在isa_probe.sh用 hipcc 内联汇编逐条试 v_mmac/v_mfma/v_dot* 能不能编过 → 发现 gfx936 吃 v_mmac。
② 确认是 16-deep 点积mmac_verify.hip喂 A=B=全 1,看 C 每个元素是不是 =16(=Σ 16 个 1×1)。是 → 确认语义。
③ 独热探针定位mmac_layout.hip / mmac_solve.hip / mmac_frag.hip只让某一个 (lane, 槽) = 1、其余全 0,看 C 的哪个位置变非零 → 反推这个槽对应矩阵哪个元素。逐槽测,拼出完整映射。
④ 暴力兜底 / 对拍mmac_brute.hip / mmac_btile.hip暴力搜布局组合,与 CPU 参考找 bit-exact 的那一组;B=单位阵专解 B 布局。
⑤ 反汇编验证gcn_decode.py / gcn_scan.py把 kernel 的机器码 .text 解码,统计真发了哪些指令(确认热循环用的是矩阵核 v_mmac,不是退化成普通 FMA)。
独热法核心思想(mmac_solve.hip 注释)
// 每次只让 A 的一个 fragment 槽(lane L, slot i)=1 其余=0,B=全1
// → C 的非零位置揭示 "a_frag[L][i] 参与了哪个输出行" → 反推 a_frag[L][i]=A[?][?]
动手实践 1 · 跑探针在 DCU 宿主机编译并运行 mmac_verify.hip 看是否打印每元素=16;再跑 bash isa_probe.sh 看哪几条矩阵指令 OK(应看到 v_mmac OK、v_mfma 多半 FAIL)。这一步让你亲眼确认"为什么是 v_mmac"。

4gemm_lib_mmac.hip 逐段讲解↑

文件位置:最优项目代码/02_matrix_core_HIP/gemm_lib_mmac.hip(172 行)。它就是编出 libgemm.so 的源码。下面拆 5 段。

4.1 类型定义 + builtin

这段干啥:定义向量类型 —— half4(4 个 fp16,给 a/b)、f32x4(4 个 fp32,给累加器 c)、half8(一次搬 8 个 fp16,加速访存)。__fp16 是 HIP 的半精度标量类型。

gemm_lib_mmac.hip · L15–L17
typedef __fp16 half4 __attribute__((ext_vector_type(4)));   // a/b 片段:4 个 fp16
typedef float  f32x4 __attribute__((ext_vector_type(4)));   // c 累加器:4 个 fp32
typedef struct __align__(16) { __half2 a,b,c,d; } half8;       // 一次搬 8 个 fp16(向量化访存)

4.2 mmac_gemm 核:LDS-tiled 矩阵核 GEMM

这段干啥:真正算 GEMM 的 kernel。模板参数 <WAVES,NB,KB,PAD> 决定 tile 大小(一个 block 算 BM×BN = (WAVES·16)×(NB·16) 的输出)。流程三步:① 把这块要用的 A、W 从 HBM 搬进 LDS(共享内存,用 half8 一次 8 个);② 同步后,逐 16-K 调 v_mmac 累加;③ 把累加器写回 HBM(顺带加 bias)。

gemm_lib_mmac.hip · L23–L83(节选骨架)
template<int WAVES, int NB, int KB, int PAD>
__global__ __launch_bounds__(WAVES*64)
void mmac_gemm(const __half* A, const __half* W, const __half* bias,
               __half* C, int M, int N, int K) {
  __shared__ __half As[BM*(BK+PAD)], Ws[BN*(BK+PAD)];     // LDS tile(PAD 避 bank 冲突)
  int wave=tid>>6, lane=tid&63, r=lane&15, g=lane>>4;     // ★就是 3.2 的 r,g
  f32x4 acc[NB] = {0};                                    // 每 wave 管 NB 个 16×16 输出

  for(int k0=0; k0<K; k0+=BK){            // 沿 K 分块
    // ① 协作搬 A、W 进 LDS(half8 向量化,边界用标量补)
    for(int u=tid; u<A_units; u+=TPB) *(half8*)&As[...] = *(half8*)&A[...];
    __syncthreads();
    // ② 逐 16-K 调矩阵核(a 取一次,对 NB 个 b 各乘一次)
    for(int ks=0; ks<KB; ks++){
      half4 a = *(half4*)&As[(wave*16+r)*LDK + ks*16 + g*4];   // a_frag[i]=A[r][g*4+i]
      for(int j=0; j<NB; j++){
        half4 b = *(half4*)&Ws[(j*16+r)*LDK + ks*16 + g*4];  // b_frag[i]=W[r][g*4+i]
        acc[j] = __builtin_amdgcn_mmac_f32_16x16x16f16(a, b, acc[j]);  // ★矩阵核
      }
    }
    __syncthreads();
  }
  // ③ 写回:acc[j][i] = C[行 wave*16+r][列 j*16 + g + i*4] (+bias)
  for(int j=0;j<NB;j++) for(int i=0;i<4;i++){
    int gm=blockM+wave*16+r, gn=blockN+j*16+g+i*4;
    if(gm<M&&gn<N){ float v=acc[j][i]; if(bias)v+=bias[gn]; C[gm*N+gn]=v; }
  }
}
把 4.2 和 3.2 对上号(关键)

读 a 的地址 As[(wave*16+r)*LDK + ks*16 + g*4] 取连续 4 个 = a_frag[i]=A[r][g*4+i];写回 gn=...+g+i*4 = acc[i]=C[r][n=g+i*4]。代码里每个下标都来自 3.2 那张逆向图。这就是"逆向布局 → 落到代码"的闭环。

4.3 gemm_init:不调 rocblas_initialize(省 121MiB 的那一行)

这段干啥:这是整个 U +0.32 分的"那一行"——或者说"故意不写的那一行"。rocBLAS 版会在这里 rocblas_initialize();matrix-core 版绝不调它,因此 Tensile 库不被加载,121MiB 省下。它只用极小张量把自己的模板 kernel 预热一遍(消首样本懒加载),保持 V 的稳态。

gemm_lib_mmac.hip · L87–L96
extern "C" void gemm_init() {
  // ★关键:不调 rocblas_initialize → 不加载 Tensile 库 → 省 121MiB
  // 只用极小张量触发各 mmac 模板 kernel 懒加载(移出评测计时区)
  __half *a,*w,*c; hipMalloc(&a,16*16*2); hipMalloc(&w,16*16*2); hipMalloc(&c,16*16*2);
  _gemm_warm(a,w,c);            // 预热所有会用到的 tile 模板实例
  hipDeviceSynchronize();
  hipFree(a); hipFree(w); hipFree(c);
}

CppRunner 的 init()(L1 见过)调的就是这个 gemm_init。换库无非是把 gemm_lib.hip 编的 .so 换成 gemm_lib_mmac.hip 编的 .so,函数名(ABI)完全一样,Python 端一行不改。

4.4 gemm_linear_fp16:per-shape tile 选择(96.06→96.12 的 +0.07)

这段干啥:对外暴露的入口。不同形状的 GEMM 用不同 tile 最快——这就是 "per-shape-v3"。linear(L1 的封装)最终调到这里。

gemm_lib_mmac.hip · L102–L124
extern "C" void gemm_linear_fp16(const void* x, const void* W, const void* bias,
                                 void* out, int M, int N, int K, void* stream) {
  // ★按形状选最优 tile(在真实 chunked 形状上实测 sweep 出来的)
  if (M <= 512)        LAUNCH(2,2,2,8);   // 极小 M(recovery2d chunk):32×32,1.05×
  else if (N >= 1536)  LAUNCH(8,16,1,8); // 大 N(recovery3d chunk):128×256,2.10×
  else                LAUNCH(4,4,2,8);   // 通用(qkv/mlp/embed):64×64,~1.9–2.3×
}
迁移价值

换方向后形状会变。加一档很简单:测出新形状(打印 M,N,K),给它配个 tile,在这里加个 if。这就是 per-shape 调优——不改算法,只换"这个形状用哪号 tile"。

4.5 layernorm / swiglu(沿用,顺带提供)

同一个 .so 还提供 layernorm_fp16 和 swiglu_fp16(普通 elementwise/归约 kernel,非矩阵核),因为 CppRunner 也要调它们。它们用 wave64 内 __shfl_down 归约(注意是 64 宽,不是 NVIDIA 的 32)。这部分和 rocBLAS 版完全一致,不是本课重点。

5hipcc 编译成 libgemm.so↑

常见坑

① 忘了 --offload-arch=gfx936 → 编出来跑不动或算错。② 在登录节点编(没 DCU)→ 要 ssh 到计算节点宿主机(见 L… 环境课)。③ DTK 版本换了 → builtin 名可能变,重新 isa_probe.sh 确认。

收小结:这一课你掌握了什么↑

  • 为什么手写:rocBLAS 的 Tensile 常驻 ~121MiB,弃之换矩阵核 = U +0.32(且不慢、bit-exact)。
  • v_mmac:gfx936 的矩阵核指令(≠ AMD v_mfma),一条算 16×16×16 fp16 矩阵乘加,builtin __builtin_amdgcn_mmac_f32_16x16x16f16。
  • fragment 布局:lane→元素 的对应(r=lane%16 选行,g=lane/16 选 K/N 组),无文档,用独热探针 + isa_probe + 反汇编逆向出来,落进 kernel 每个下标。
  • gemm_lib_mmac.hip:LDS-tiled mmac_gemm 核 + gemm_init 不调 rocblas(省 121MiB)+ per-shape tile(V+0.07)+ 同 ABI drop-in 替 rocBLAS。
